# Runbook: Deploying to Render

The backend deploys to [Render](https://render.com) as a Docker web service plus
a managed PostgreSQL 16 database, defined declaratively in the repo-root
[`render.yaml`](../../render.yaml) blueprint. The image is the **`prod` stage**
of `backend/Dockerfile`; the container entrypoint is `backend/scripts/start.sh`,
which applies migrations and then serves the app with Gunicorn.

## Normal deploy flow

1. Merge to the deploy branch. `autoDeploy: true` in `render.yaml` means Render
   builds and deploys every push to the tracked branch — there is no manual
   deploy step in the happy path.
2. Render builds `backend/Dockerfile` with context `./backend` (static files are
   collected at image-build time and served by WhiteNoise).
3. On container start, `scripts/start.sh` runs `python manage.py migrate
   --noinput`, then starts Gunicorn on `$PORT` with `$WEB_CONCURRENCY` workers
   (default 3). Access and error logs go to stdout.
4. Render health-checks `GET /healthz/` (no auth, no DB access; returns
   `{"status": "ok"}`). The new instance only receives traffic after the health
   check passes; a failing health check keeps the previous deploy live.
5. Verify: open `https://<service>.onrender.com/healthz/` and spot-check an API
   endpoint, e.g. `POST /api/v1/auth/login/`.

## First-time setup (new environment)

1. In the Render dashboard, create a **Blueprint** pointing at the repository;
   Render reads `render.yaml` and provisions the `vbb-backend` web service and
   the `vbb-db` Postgres 16 database.
2. Confirm the generated env vars (below), then let the first deploy run.
3. Create an admin account from the service **Shell** tab:
   `python manage.py createsuperuser`.

## Environment variables

Set by the blueprint (do not set by hand):

| Variable | Source |
| :--- | :--- |
| `DJANGO_SETTINGS_MODULE` | `config.settings.prod` (blueprint value) |
| `SECRET_KEY` | Generated by Render (`generateValue: true`) |
| `DATABASE_URL` | Wired from the `vbb-db` database connection string |
| `WEB_CONCURRENCY` | Gunicorn worker count (blueprint value: `3`) |
| `RENDER_EXTERNAL_HOSTNAME` | Injected by Render; `prod.py` appends it to `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` automatically |

Optional overrides (see `backend/.env.example` and `config/settings/prod.py`):

| Variable | Purpose |
| :--- | :--- |
| `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` | Extra hostnames/origins (comma-separated), e.g. a custom domain |
| `SECURE_SSL_REDIRECT` | Defaults to `True` in prod |
| `DJANGO_LOG_LEVEL` | Defaults to `INFO` |
| `CONN_MAX_AGE` | DB connection persistence, defaults to `600` |
| `EMAIL_BACKEND`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `DEFAULT_FROM_EMAIL` | SMTP; falls back to the console backend if unset |
| `FRONTEND_URL` | Client origin used in allauth email/reset links |
| `NOTIFICATION_ADAPTERS` | Comma-separated delivery adapters, e.g. `stdout,fcm` (default `stdout`) |
| `GOOGLE_APPLICATION_CREDENTIALS` / `FIREBASE_CREDENTIALS` | Path to Firebase service-account JSON; without it FCM delivery is simulated |
| `INVENTORY_LOW_STOCK_THRESHOLD`, `INVENTORY_STANDARD_EXPIRY_DAYS`, `FACILITY_WOREDA_MAX`, `API_PAGE_SIZE` | Domain constants (see `docs/CONTEXT.md`) |

## Migrations

- Migrations run automatically on every container start (`start.sh`). There is
  no separate migrate step to trigger.
- A migration failure aborts start-up (`set -e`), the health check never passes,
  and Render keeps the previous deploy serving traffic. Read the failing
  migration in the deploy logs, fix forward, and push again.
- To run a migration command by hand, use the service **Shell** tab:
  `python manage.py showmigrations` / `python manage.py migrate <app> <name>`.

## Rollback

1. Render dashboard → service → **Deploys** → pick the last good deploy →
   **Rollback**. This redeploys the previous image; it does **not** reverse
   database migrations.
2. If the bad deploy included a migration, prefer fixing forward. Only reverse a
   migration (`manage.py migrate <app> <previous_migration>`) if you have
   confirmed it is safely reversible; back up first (Render Postgres → Recovery,
   or `pg_dump` with the external connection string).
3. If `autoDeploy` keeps re-deploying the broken commit, suspend auto-deploy or
   revert the commit on the tracked branch.

## Symptoms → diagnosis → remedy

| Symptom | Diagnosis | Remedy |
| :--- | :--- | :--- |
| Deploy stuck "in progress", old version still live | Health check `/healthz/` failing on the new instance | Read deploy logs; usually a migration or import error at start-up |
| 400 Bad Request on every route | Host not in `ALLOWED_HOSTS` (custom domain) | Add the domain to `ALLOWED_HOSTS` env var |
| CSRF failures from the admin or web client | Origin missing from `CSRF_TRUSTED_ORIGINS` | Add the `https://` origin to `CSRF_TRUSTED_ORIGINS` |
| 500s mentioning the database | `DATABASE_URL` broken or DB unavailable | Check the `vbb-db` status; verify the env var wiring in the blueprint |
| Static files 404 / unstyled admin | `collectstatic` failed at image build | Check the build logs for the `collectstatic` step |

Logs: all application, Gunicorn, and dispatcher output goes to **stdout** and is
available in the Render dashboard **Logs** tab (see
[incident-response.md](incident-response.md)).
